# Humanize 理念下的 Kei 能力扩展设计

状态：设计稿 v2，2026-11-20。v1 把预算当主线（错的），本版改为**能力优先**：
配额只做异常保护，主线是让 Kei 跑得更久、能做更多类型的活、能被独立复核、失败能自己接力。
P0（进展驱动续跑）已落地，C1–C4 待拍板。

## 一、结论

Kei 现在的短板不是「跑得太久会烧钱」，而是**能力边界**：会话一长就退化、只会干代码这一种活、
切片完成与否自己说了算、指标记了不回用、目标一停就彻底死掉等人叫。
配额的价值只在于防跑飞；把它当设计主线，等于把 agent 越改越笨。

## 二、参照：Humanize 的五条结论

来源：张子健（清华人工智能学院博士生 / NVIDIA Research Singapore）的技术博客与开源实现
`humanfia/humanize`（Apache-2.0，Flow 索引 `humanfia/flowverse`）。文中成绩多为作者自述，
此处只取方法论，不引用未经复核的数字。

1. **没有万能 Flow**：不同问题类型要匹配不同调度形态，所以先扩类型，再谈统一。
2. **模型多样性优于单模型**：同模型写、同模型审等于没审；关键结论换模型独立复核。
3. **朴素并行无效**：并行要有可测指标与判据，否则只是把错误放大。
4. **渐进式目标优于一次性大目标**：小步推进、每步可验收，让长活能一直往下走。
5. **长会话会退化**：连续 3–5 小时后单次回复 token 缩水约 30%–45%，
   做法是果断换会话、把成果留在工作区，而不是靠压缩上下文硬撑。

## 三、现状：能力缺口，不是配额缺口

- **只能干一类活**：`code` 之外的调研、运维、评审，全都塞进同一条 chat + 工具循环。
- **会话会退化**：`ThreadState` 只有 `AGENT_THREAD_MAX_TOKENS`（60000）一个压缩闸门，
  没有时间与轮数概念；一个工程群可以几十轮不换会话，越跑越糊。
- **自评自判**：切片 `done` 由同一个模型在同一条会话里自己宣布。
- **指标不回用**：`data/calls/` 有轮数、token、缓存率、工具耗时，但没有一处拿它做决策。
- **一停就死**：预算到点转 `paused`（v1 的做法），目标自己不会重新起来。
- **观测缺失**：11-19 15:54 之后 `data/calls` 零次 `purpose=chat`，日志却在每两分钟报「已接上」，
  群里看到的是「卡住」，实际是空转 —— 这类「看着在动」比停下来更糟。

## 四、设计：C1–C5

### C1 无限续航：换会话，不是停会话

对应结论 5。

- `ThreadState` 增 `bornAt`；到 `AGENT_THREAD_MAX_AGE_MS`（默认 3h）或 `AGENT_THREAD_MAX_TURNS`（默认 30）
  时**不停止工作**，而是先写交接单、再重建会话：
  `data/handoffs/<chat>/<ISO>.md`，内容 = 当前目标与切片、本轮改动文件、验证结论、下一步。
- 重建后的第一条 user 消息注入交接单前 800 字，随后照常干活。token 压缩（60000）降为最后兜底。
- 能力含义：一个目标可以连续跑一整天，质量不随会话变长而衰减。
- 验收：`agent:check` 造 31 轮会话，断言 `threads` 被重建且 `data/handoffs` 多一份文件。

### C2 多模型接力：谁擅长什么就交给谁

对应结论 2、3。

- 环节拆成四种角色，各自可配模型 preset：
  `plan`（拆片与判据）、`exec`（改代码/跑命令）、`review`（独立复核）、`summarize`（收尾与记录本）。
  默认全部走现有 `deepseek-v4.1-flash`，`AGENT_PLAN_MODEL` / `AGENT_REVIEW_MODEL` 可单独换。
- 同一片允许**异构并行两版**（不同模型各出一版 diff），用测试与指标选，不靠自我感觉；
  这条只在有判据可测时开（结论 3）。
- 能力含义：从「一个模型硬扛所有环节」变成「按环节配最合适的模型」，且天然获得第二意见。
- 验收：`agent:check` 断言四种角色各自读得到自己的 preset，缺省回落到主模型。

### C3 独立复核：done 之前换空上下文审

对应结论 2。形式对齐 RLCR 的「必须换模型独立审」。

- `goal_step(status=done)` 前强制过复核：新会话、空上下文，只喂三样——
  切片判据、`git diff --stat` 与关键 diff、验证命令真实输出。
- 复核模型取 `AGENT_REVIEW_MODEL`；只有单一模型时退化为温度 0 + 空上下文，并标注「同模型复核，弱」。
- 输出 `PASS` / `FAIL` + 一句理由，落 `data/reviews/<chat>/<slice>.json`。
  `FAIL` 不是失败，是**退回 review 继续改**，切片状态自动回到 `review`。
- 能力含义：agent 第一次拥有「自己看不见自己错」的补丁。
- 验收：`agent:check` 断言 FAIL 场景切片停在 `review`，PASS 才变 `done`。

### C4 任务类型扩展：让 Kei 能干的活变多

对应结论 1。

- 目标加 `kind`：`code` / `research` / `ops` / `review`，缺省 `code`。
- 每个 kind 配一套**能力包**（工具 + 提示词 + 判据模板），是「加能力」不是「减工具」：
  - `code`：CNB 派工、本机验证、PR 复核（现有）
  - `research`：web 搜索、抓页面、多模型并行初稿 + 交叉审、结论必须带出处
  - `ops`：只读体检、日志分析、配置变更带回滚点
  - `review`：读 diff / CI / issue，产出评审意见，不写仓库
- 提示词按 kind 拼装；工具面按 kind 取并集，缺省仍是全量（owner/dev 同权不变）。
- 能力含义：Kei 从「代码管家」扩成「项目管家」，调研、巡检、评审都能接。
- 验收：`agent:check` 断言四种 kind 的能力包各自可见且互不覆盖。

### C5 进展驱动续跑：配额只做异常保护

对应结论 4。**P0 已实现**。

- 判据从「还剩多少轮」改成「上一段有没有推进」：切片状态变化（`goal_step`）即记一次进展，
  `budget.roundsSinceProgress` 归零；每跑一轮 +1。
- 轮数/墙钟到点：`roundsSinceProgress === 0` 且有下一片 → **自动续命**（重置这一段预算，
  `budget.renews` 计数，群里报一句「🔁 续命第 N 次」）；有积压才停。
- 只有连续空转（`roundsSinceProgress > 0`）才转 `paused` 并出声要人给方向，`/goal resume` 续上。
- 巡检 `runGoalSweep` 只统计真正排上定时器的群，不再假报「已接上」。
- 能力含义：能干活的就一直干，卡住的才找人；日志与群里看到的状态和实际一致。
- 验收：`agent:check` 新增「没进展计空转轮数 / 切片一动手就算有进展 / 续命后预算重置 / 续命后能继续跑」。

## 五、保留的三道安全阀（唯一允许的限制）

这些是防跑飞，不是给能力上锁，任何一条触发都要在群里出声：

1. 同一工具调用重复 3 次 → 收尾并报原因（防死循环）。
2. 连续空转（无切片进展）到预算边界 → 停下问人（C5）。
3. 主动推送优先（`deliver()` 先 `pushText`），失败退回被动回复并记日志（防消息丢）。

## 六、落地顺序

- **P0（已落地）**：进展驱动续跑 + 续命计数 + 巡检不再假报；`paused` 只留给「无进展」。
  回滚 = revert 该提交 + 重启。
- **P1**：C1 交接单换会话（风险中等，观察 cacheRate 与首调 p50）。
- **P2**：C3 复核通道 → C4 kind 能力包 → C2 多模型接力（C2 依赖前三者给出的角色边界）。
- 每步必须带 `agent:check` 断言；没有断言的改动不进 main。

## 七、明确不做

- 不重造工具调用循环：CodeBuddy / NPC 的 agent 循环当黑箱调度，Kei 只负责派活、探针、验收。
- 不引入向量库或第二套记忆：记录本 + 目标账本 + 交接单三段够用。
- 不把「省钱」写成设计目标：省钱是观测指标，用来选更合适的流程，不是砍能力的理由。
- 不为了「看起来在动」加心跳播报；只有状态真的变了才出声。
